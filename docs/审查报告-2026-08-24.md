# PlugKit 项目整体梳理与审查方案

- **审查日期**：2026-08-24
- **审查范围**：全量源码（Rust 后端 17 文件 ~3.8k 行、Vue 前端 ~2k 行、3 个插件 UI+CLI ~2.6k 行、发布脚本 9 个、测试 3 个）
- **审查方式**：逐模块专项审查（阶段一）→ 全局综合审查（阶段二）
- **约束**：不修改外部接口契约、禁止跨模块重构、不变更业务行为，仅局部修复

---

## M3 任务执行模块

| # | 位置 | 问题描述 | 风险等级 | 修复建议 |
|---|---|---|---|---|
| M3-1 | `tool_runner.rs:124-130` | **`invoke` 前置校验（read_manifest / 命令查找 / find_executable）用 `?` 提前返回，发生在 register 之前**。此时 `invoke_cli` 已在 task_queue 创建任务（Pending）→ 校验失败后**任务永久停留在 Pending**，任务中心显示"等待中"却永不执行 | **【必须修复】** | 把前置校验包入统一错误路径：失败时 `update_status_with_error(Failed)` + `unregister` |
| M3-2 | `tool_runner.rs:254,219` | 取消/超时只 `child.kill()`（kill_on_drop 同理），**只杀直接子进程**；Unix 下 yt-dlp 拉起的 ffmpeg 在独立进程组内会残留为孤儿继续下载 | **【建议优化】** | Unix 对进程组发 SIGTERM（`kill -- -pid`），Windows 用 `taskkill /T` |
| M3-3 | `tool_runner.rs`（全文） | **无任务超时机制**：`SecurityError::Timeout` 定义了未使用。json 模式命令（list-formats/probe/list）网络卡死时任务永久 running（cancel 恒检查已覆盖人工取消，但无人值守场景挂死） | **【建议优化】** | 对 json 模式命令加超时（如 5 分钟）；progress 模式（长下载/转换）不加 |
| M3-4 | `tool_runner.rs:336-378` | 暂停中取消：先 resume 再 kill，存在短暂竞态窗口（进程恢复后继续执行一小段） | **【建议优化】** | resume 与 kill 之间无等待必要，可接受；或 kill 前不 resume（SIGKILL 对 STOP 无效，需 SIGCONT 后立即 SIGKILL，当前做法正确）→ 保留现状，仅注释说明 |
| M3-5 | `tool_runner.rs:169-177` | 任务工作目录 `~/.plugkit/tmp/{plugin}/{task_id}` 崩溃/kill -9 时残留，无启动清理 | **【建议优化】** | 启动时清理 `~/.plugkit/tmp` 下陈旧目录（与 task recover 同批） |
| M3-6 | `task_queue.rs:226-262` | `cancel/pause/resume` 无状态前置检查：对已完成/已取消任务调用会产生**非法状态迁移**（Completed → Cancelled / → Paused） | **【建议优化】** | 仅活跃状态（pending/running/paused）可操作，其余忽略 |
| M3-7 | `tool_runner.rs:324-328` | 最后一行若为 progress（协议违规），静默返回 progress 数据而非报错 | **【建议优化】** | 校验最后一行类型为 result/error，否则报"插件输出协议违规" |

**M3 补充说明**：并发信号量（5）+ 排队可取消 + 进程组 SIGSTOP/SIGCONT 暂停 + `_reserve_path` O_EXCL 防覆盖 + percent clamp + task 崩溃 recover，任务体系整体设计成熟。

# 阶段二：全局综合审查

## 整体评估结论

**架构健康度：高。** 零业务逻辑外壳 + CLI/iframe 插件的分层干净，模块边界清晰，安全基线扎实（Zip-Slip 词法归一化双重防线、插件页面 CSP 注入、iframe 身份校验、sha256/Ed25519 校验、路径归一化、三级报错链路、并发信号量、任务崩溃恢复、原子文件替换）。任务中心-桥接-插件-日志的错误闭环是本项目最成熟的部分。

**主要风险集中在 4 个面**：
1. **状态机闭环缺口**（M3-1 卡 Pending、M1-2 卸载状态不一致）——不常触发但一旦触发用户困惑且无自愈路径；
2. **跨平台适配硬伤**（Windows PATH 探测失效、`stat` BSD 语法、路径分隔符、沙盒 alert 阻断）——当前 macOS 主开发掩盖了这些问题，但 manifest 声明支持 4 平台；
3. **发布门禁有真实缺口**（binaryUrl 空 tag 已入库、tauri CLI 未声明）；
4. **插件不可信边界不彻底**（task_id 归属未校验、CSV 公式注入、无校验下载窗口）。

**业务流程闭环检查**：安装闭环 ✅（缺依赖警告透出）；任务闭环 ✅（卡 Pending 缺口）；卸载闭环 ✅（删除失败不一致缺口）；下载链路闭环 ✅；发布闭环 ✅（tag 校验缺口）。

## G-6 共享代码方案说明（供确认）

**问题**：download 与 playlist 两个插件 CLI 共享大量相同逻辑——`progress/result/error/dep/cookies_args/parse_args/brief` 及 `diagnose_ytdlp_error`（约 110 行 yt-dlp 错误诊断）。任何修改（新增错误分类、调整网络参数、修复诊断规则）都需要**改两份**，极易漏改导致两插件行为不一致（历史上已多次同步修改）。

**方案对比**：

| 方案 | 做法 | 优点 | 缺点 | 推荐度 |
|---|---|---|---|---|
| A 保持现状 | 继续双份复制维护 | 零改动、插件完全独立 | 改一处漏一处，行为漂移风险持续 | ✗ |
| **B 公共模块随包分发**（推荐） | 新增 `plugins/shared/_common.py`（公共源码单点）；package-plugins.sh / sync-plugins.sh / dev-watch.sh 打包/同步时复制进各插件 `tool/`；CLI `from _common import ...` | 单点维护，改一处全插件同步；协议/错误码/网络参数行为统一；不改变插件独立分发架构 | 每插件包仍含副本（体积 +几 KB，可接受）；打包脚本需联动复制（一次性改造） | ✓ |
| C 下沉外壳 | 公共逻辑移入 Rust 外壳（如错误诊断放 message_bridge） | 插件瘦身 | **违反"零业务逻辑外壳"架构原则**；诊断是插件业务；跨语言耦合 | ✗ |

**结论**：推荐 B——公共逻辑从"双份复制"变为"单点源 + 打包时复制"，行为一致性由构建脚本保证（每次打包必然同步），同时保持插件可独立分发、外壳零业务逻辑。请确认是否采用方案 B。
